# HelloDog 海外个人用户商业化计划

日期：2026-09-12。目标用户已由产品负责人确认：海外个人用户，主要用于日常聊天。

本文是产品与实施建议，不代表这些功能已经完成，也不代表正式上线。继续沿用“暂不上线”的安排。本轮只核对现有代码、发布记录与官方资料，未重新运行客户端验收，未修改线上套餐、余额、支付、网站或数据库。

## 1. 产品方向与首版边界

建议把 HelloDog 定位为“帮助不同语言的人顺畅聊天的桌面翻译助手”。付费价值应体现在稳定的双向翻译、自然且忠实的表达、联系人语言记忆、清楚的用量和可靠的恢复能力。

首批可邀请经常与外国朋友、伴侣或家人聊天的人，以及确实使用 Windows 桌面聊天的海外居民。优先验证他们是否持续需要桌面翻译，以及为什么愿意付费。不要把“海外个人用户”直接等同于“每天用 Windows 聊天的用户”。

三个身份要分清：HelloDog 登录账户管理购买记录和字符余额；WhatsApp/Signal 账户负责原平台聊天；管理员账户负责运营。购买字符、移除聊天账号、退出登录是不同操作。

首版建议：Windows、WhatsApp/Signal 已验收的聊天流程、文字双向翻译、三个字符包、个人钱包和自助帮助。基础翻译质量、隐私保护、恢复能力对各档用户一致。聊天账号数量以实际稳定性测试为准。

先后置团队席位、CRM、群发、营销自动化、代理分销、大量新增平台、实时通话翻译。它们会扩大维护和客服成本，也不直接解决这批个人用户的主要需求。

## 2. 当前基础与商业化缺口

根据本地 0.5.3-beta.2 发布与验收记录，已有设置齿轮、一键重启、统一刷新、草稿与任务恢复、历史翻译请求复用、原文字符记录、实际 API 用量记录和账户隔离等基础。记录显示 265 项自动化回归通过，并完成独立测试目录中的真实进程重启及组件刷新。

这些是现有记录的核对结果，不是本次重新执行的测试，也不能替代真实联系人聊天、媒体和通话验收。当前安装包仍是未签名的本地测试版。

| 商业化缺口 | 完成标准 |
| --- | --- |
| 真实聊天稳定性 | 中英文输入法、连续发送、断网、休眠、媒体、通话和重开逐项有实机记录 |
| 购买与到账 | 一笔成功付款只加一次字符；漏通知、重复通知、退款均能对账 |
| 用户用量透明 | 客户端、字符账本和实际 API 成本可以对应；不能用推算成本冒充供应商账单确认 |
| 隐私清理 | 限时/删除消息不会残留在 HelloDog 译文缓存中，迟到结果也不能恢复已删除内容 |
| 账户保护 | 唯一主管理员增加二次验证和恢复方式；普通用户能恢复账户及余额 |
| 安装和更新 | 签名、覆盖安装、更新中断、失败恢复和数据格式兼容均完成验收 |
| 对外说明 | 官网功能表、实际截图、支持系统、计费规则、退款和隐私说明与软件一致 |

原有后台已有用户、字符调整、账本和成本管理基础。完整自助支付及退款流程仍需补齐；历史后台记录不作为当前线上状态的实时证明。

## 3. 新用户前十分钟

建议将首次体验控制在六步内：选择界面语言；登录或注册 HelloDog；关联一个聊天账号；选择自己与对方的语言；理解云翻译的数据使用并启用；完成一次真实翻译或明确标注的示例体验。

试用不要求先填银行卡。关联失败要给出具体原因和恢复入口，不能困在二维码、验证邮件或加载动画里。验证邮件支持重新发送和纠正邮箱，并保留当前流程进度。

首次只引导一个账号、一个联系人。不要让用户先填写代理、API Key、模型名称或复杂术语。普通用户使用 HelloDog 提供的服务即可。

英文界面优先完整覆盖聊天、购买、错误、帮助和邮件；第二种界面语言按试用人群决定。价格、日期、时区和数字格式跟随明确的地区设置。不能把用户的中文管理习惯直接复制到海外消费者界面。

## 4. 套餐建议

先采用预付字符包，用完自行补充。付费字符不按月自动清零，不默认自动续费。若业务决定设置有效期，应在购买前明确日期、到期规则及提醒，不能事后缩短，也不轻率承诺永久服务。

| 档位 | 首轮建议容量 | 用途 |
| --- | ---: | --- |
| 免费试用 | 5,000 字符 | 体验真实发送、接收、语言记忆和恢复；一次性领取 |
| 轻量包 | 50,000 字符 | 偶尔进行跨语言聊天 |
| 常用包 | 200,000 字符 | 有持续聊天对象的个人用户 |
| 频繁包 | 500,000 字符 | 较频繁的双向文字聊天 |

容量是试用假设，美元售价尚未核定。先收集至少两周真实成本和使用分布，再结合支付手续费、客服成本及试购反馈确定价格。不要先设置很大的折扣或终身套餐。

假设每天实际翻译 40 条消息，每条平均 45 个原文字符，使用 30 天，则消耗 54,000 字符。每天 150 条、每条 60 字符、使用 30 天则是 270,000 字符。这只是计算示例，不是用户实测，也不是“一个套餐能发多少条”的保证。

消费者同时看到“总价、字符数、每万字符单价、有效期规则”。积累足够个人用量后，可显示“按你最近的使用量预计可用多久”，注明估算依据。不要在数据不足时编造可用天数。

付费、赠送、故障补偿字符分别记账。赠送额度可以有明确到期日；按公开规则优先使用先到期的额度。管理员赠送不算销售收入，也不自动成为可提现余额。按月订阅、自动补充和家庭共享等有复购数据后再评估。

## 5. 先确定一份用户能看懂的扣费规则

| 操作 | 建议的字符处理 |
| --- | --- |
| 第一次成功得到可用译文 | 按本次原文字符数扣一次；正常聊天不用每条审核 |
| 接收翻译 | 与发送翻译同样计费；首次开启时说明双向消耗 |
| 同一任务重复点击、重试、重开、恢复缓存 | 不新增扣费，继续使用原任务和原结果 |
| 不同消息文字刚好一样 | 仍是不同消息，可以根据各自上下文分别翻译；不能只按文字合并 |
| 纯表情、媒体本身、无需翻译的内容 | 不调用付费文字翻译，不产生该项字符费 |
| 恢复已翻译历史 | 不重复扣费 |
| 首次翻译尚未翻译的历史 | 正常计费；默认不因滚动或打开旧会话而批量启动，批量操作先显示范围和消耗上限 |
| 超时、结果未知 | 暂时保留原请求待核对；不新建请求盲重试，预留额度与已扣费分开显示 |
| 系统识别到失败、空译文或不可用结果 | 不扣费；已结算则自动退回字符并留记录 |
| 译文可用，但聊天平台发送失败 | 翻译费用仍计一次；重用已有译文发送不再收翻译费，不能把译文完成显示为已送达 |
| 本地手动修改译文 | 免费，不自动调用模型 |
| 主动改原文、目标语言、语气后重新翻译 | 属于新操作；该入口说明会再计费，不给普通发送增加确认步骤 |
| 余额不足 | 暂停新增付费翻译，保留草稿和已有结果；用户可明确选择发送原文，系统不能偷偷改发原文 |

需要专门打通“服务端已结算、客户端随后发现译文不可用”的自动退字符路径。不能只在客户端提示失败，后台却保留成功扣费。

当前计数实现按去除首尾空白后的 Unicode 码点计算，内部空格、标点等包含在内；组合表情可能由多个码点组成。首个商业计费版本应明确该口径，并确保前端预览和服务端一致。纯表情无需翻译时应直接跳过。不要宣传“一张可见表情固定算一个字符”，也不要静默改变旧订单口径。

给用户计算的是实际本次原文，不把系统提示词、上下文和输出再算成用户字符。若以后改变口径，应有计费版本和生效规则。

缓存内容与防重复扣费记录应分别管理。清理内容、换电脑和重新安装后，仍可通过云端原请求记录判断是否处理过。若结果按用户隐私设置已不可恢复，应说明情况，由用户决定是否新译，不能自动再次收费。

## 6. 用户字符和真实美元成本分别记账

字符是消费者购买的计量单位，Tokens 是供应商计价单位，二者不能按一个固定比例直接结算。DeepSeek 官方明确应以每次返回的 usage 为准，字符比例只是近似值。[官方用量说明](https://api-docs.deepseek.com/quick_start/token_usage/)

对每次 API 调用保存：供应商、实际模型、调用时间、供应商请求编号、输入 Token、缓存命中输入 Token、输出 Token、使用的单价版本、原始币种和费用状态。缓存输入不能重复加在总输入上；推理 Token 是否已包含在输出中按供应商字段定义处理，不能再重复相加。

每次模型费用按当次适用的缓存输入、非缓存输入和输出单价分别计算。模型版本、峰谷时段和单价变化要保留历史快照，不能用今天的价格回算昨天全部调用。实时聊天不应为了等待低价时段被拖延。[官方模型定价](https://api-docs.deepseek.com/quick_start/pricing/)

每百万已计费字符对应的 API 成本 = 同一统计范围内实际发生的 API 成本 ÷ 同范围已计费字符数 × 1,000,000。API 成本需包含由 HelloDog 承担的失败、重试和赠送试用成本，并能分开查看。短消息多、上下文长和不同语言组合都会影响结果。

定价还要计入云服务、存储和下载、支付固定及比例手续费、退款或争议损耗、客服与维护。分别观察 API 毛利、变动成本后的贡献利润和扣除固定运营成本后的结果；不要把充值收入全部当作已赚利润，未使用字符仍对应后续服务责任。

后台分别显示“已按 usage 计算”“待核对”“已与供应商账单核对”。没有 usage 或供应商数据时标明缺失，不能编数字。人民币成本转美元时保留原币金额、汇率来源和日期；供应商余额变化不能替代逐项账单。

先用内部及自愿试用用户的数据测量两周，按语言、消息长度、模型和每天用量分组，只收集必要的非内容统计。最终价格需同时满足成本、用户愿付价格和实际留存，API 便宜本身不能证明产品卖得动。

## 7. 钱包和支付流程

客户端钱包只需要醒目展示可用字符、待确认额度、今日用量、购买入口与订单记录。详细 Token 和供应商价格留给管理员。未同步时显示最后同步时间，低余额在适当位置提醒，不能反复打断每条聊天。

购买流程：创建订单并固定当时的价格、币种、字符数及有效期规则；进入支付服务商结账页；服务端确认实际付款及对应订单；一次性入字符账本；客户端更新；后台定期查漏补账。

不凭网页跳回“支付成功”、付款截图或客户端传来的金额加字符。支付通知需要验签、核对金额币种和所属用户、保存处理记录，对事件和实际付款订单都去重。重复通知、乱序到达、通知丢失后补查都应得到同一个结果。Stripe 的官方说明明确存在重复和不保证顺序的事件。[支付通知说明](https://docs.stripe.com/webhooks)

客户端在付款未确认时提供“查询这笔订单”，不要诱导用户立即再付一遍。支付已成功但字符未到账，应自动恢复并可联系支持。

首版选择一个支持经营主体的支付渠道，优先使用服务商托管结账，不自行保存银行卡资料。支付方式、币种及税费展示按目标国家和经营主体确定。Stripe 等服务的商户开通有地区条件，当前不能仅凭“用户在海外”就确定可用。[商户地区说明](https://stripe.com/global)

退款应关联原订单、实际支付价格和对应付费字符批次。部分使用、折扣、赠送额度、支付争议分别处理；不能把低价购入字符按更高单价退钱。具体退款、有效期和税务条款按销售地区核定。发生支付争议时限制相关付费服务，不删除用户私人聊天来追偿。

上线前演练：重复付款通知、不同通知对应同一付款、支付后断网、漏通知、错误金额、旧订单补查、重复退款和部分退款。每笔订单必须能解释钱和字符最终去了哪里。

## 8. 聊天界面优化

主窗口优先保留聊天、联系人语言、翻译开关和简短余额。默认隐藏请求编号、供应商、队列等诊断信息；用户在账单详情或排错时再查看。

| 位置 | 具体改进 | 验收方法 |
| --- | --- | --- |
| 输入框 | 中文候选词确认不误发送；Enter/Shift+Enter 规则清楚；点击表情后焦点恢复 | 中英切换、emoji、多行、粘贴、附件连续组合测试 |
| 发送 | 输入下一条不被上一条翻译锁住；保持原会话顺序；失败能处理且不永久转圈 | 连续 20 条、切换联系人、每个阶段断网 |
| 消息气泡 | 译文不覆盖时间和回执；字体、颜色、行距可调；长文可折叠 | 多窗口宽度、缩放、高对比度及长文本 |
| 历史 | 保持滚动位置，只恢复已有译文；新历史翻译由用户主动选择范围 | 反复打开、上滚、改联系人名、重开、清理缓存 |
| 联系人设置 | 记住目标语言、昵称和专用词；默认只影响当前联系人，修改可撤销 | 两个联系人与两个账号交叉验证 |
| 刷新和重启 | 保留草稿与任务；通话、录音及未保存附件有明确处理 | 保存失败、进程退出、恢复后发送核对 |
| 错误提示 | 说明当前状态和可执行动作；避免只有“错误代码”或无限加载 | 翻译失败、平台未回执、断网分别呈现 |

翻译默认“自然但忠实”，不擅自增加亲密程度、承诺、礼貌或情绪。优先测试否定句、玩笑、昵称、口语缩写、混合语言、时间、金额和网址。对于上下文不足的短句，不把模型猜测包装成确定含义。

首批选择实际需求最多的两至三个语言组合，建立包含正常聊天和困难案例的评价集。使用自愿提供、获准处理的样本或专门编写的测试句，避免收集真实私人聊天用于训练。

## 9. 个人用户隐私和数据恢复

云翻译需要把被选中的消息文本及必要上下文交给翻译服务。这会增加原聊天双方之外的数据接收方，不能沿用“只有聊天双方能看见”来描述整个 HelloDog 翻译流程。首次启用时用简短说明告知服务商、数据范围和退出方式；完整隐私说明可展开。

建议提供按联系人停用云翻译、限制上下文、通知隐藏内容、本地记录保留期和删除账号数据入口。服务商是否保留数据、是否用于训练、保存地区和删除机制，应核实后写入政策，不能凭愿望承诺零保存。

限时消息需要贯穿原文、译文缓存、预览、通知、待处理任务和迟到响应处理。源消息消失后不能被后台任务再次写回。本地防重复处理尽量保留最少的非内容标识，并解释其保留目的。

“设置备份”“聊天记录备份”“字符余额恢复”应分开。现有 Windows 用户绑定的本机加密不能直接当作跨电脑备份。更换电脑后登录可恢复云端购买和余额，聊天账号仍需按平台要求关联，不能承诺全部聊天自动迁移。

后台默认不提供聊天正文浏览。诊断由用户预览后发送，客服主要使用版本、平台、时间、错误类型和脱敏请求编号定位问题。

## 10. 平台授权、开源和品牌

Signal Desktop 使用 AGPLv3。该许可允许收费分发，但对受覆盖代码的修改、许可说明和对应源码提供有要求；将组件放到独立进程中，不自动决定整个集成的许可边界。应审查实际组合方式、构建脚本和发布源码范围。[Signal Desktop 许可证](https://raw.githubusercontent.com/signalapp/Signal-Desktop/main/LICENSE)

开源许可与 Signal 服务条款是两个问题。服务条款包含对未经授权使用、向其服务收费及品牌使用的限制。建议收费对象明确为 HelloDog 自身翻译服务，但仅改收费名称不等于取得授权，需就实际分发、接入和品牌方案进行专业审查，必要时向平台取得澄清。[Signal 服务条款](https://signal.org/legal/)

WhatsApp 的条款同样不能被某个 GitHub 项目的开源许可替代。需要评估当前接入和修改方式是否适合公开商业分发，不能承诺官方合作、永久兼容或绝不会封号。[WhatsApp 服务条款](https://www.whatsapp.com/legal/terms-of-service)

审查结果可能改变接入方式、销售范围或某个平台是否能在首版提供；这些应在公开收费前确定，而不是先收费再补。官网对媒体、通话等能力只写实测通过的范围。

## 11. 管理后台最需要的五组能力

| 页面 | 首版必备 |
| --- | --- |
| 用户与设备 | 登录账户、地区/语言偏好、版本、最后在线时间及新鲜度；加减字符可选常用原因并留审计 |
| 订单与退款 | 已付款待到账、支付异常、退款进度、支付争议、补账入口，所有动作可查原单 |
| 字符账本 | 买入、赠送、消费、预留、释放、退回分开，客户端与云端对账，导出个人用量单 |
| 实际成本 | API 用量、模型单价快照、供应商账单核对、每用户成本和贡献利润；缺失数据单独标识 |
| 运行与支持 | 版本错误分布、服务状态、脱敏反馈、故障说明、暂停问题版本的新翻译、更新恢复记录 |

保持一个最高权限管理员，增加二次验证、恢复码和退出其他登录设备。退款、大额余额调整、修改管理凭据等高影响操作需加强验证。普通加字符提供明确用户和变动前后余额，操作原因可用预设项减少机械填写。

客户端余额更新可通过推送或轻量轮询实现，断线补拉并显示同步时间。此处优先保证一致性和可恢复，不为了把数字刷新得更频繁而增加负担。

## 12. 运维与更新

先覆盖个人常见的一个和两个聊天账号，再做五个账号稳定性测试。更多账号容量根据实际数据决定。记录启动、输入响应、切换、翻译耗时、内存和后台 CPU，区分平台、HelloDog 和网络造成的延迟。

为每个翻译请求保留统一追踪编号，但聊天主界面无需显示。供应商调用限额、日成本异常提醒和免费试用滥用控制放在后台，不让正常用户每条操作过验证。付费请求仍在云端认证、限额与记账，不能信任客户端余额或计数来决定扣款。

升级前保存草稿，使用签名与校验，优先小范围提供新版本。代码签名不保证一定没有系统信誉提示；仍需验证真实安装体验。数据格式变更应有迁移和兼容恢复方案，不能强行回退到不能读取新数据的版本。

发生某个平台兼容故障时，停止受影响的自动翻译注入并保留草稿，解释临时状态；不能继续反复提交或未经选择发送原文。运行状态页只记录服务健康，不显示私人聊天内容。

## 13. 新增功能的先后顺序

| 顺序 | 功能 | 取舍理由 |
| --- | --- | --- |
| 首版必需 | 自助购买、消费记录、低余额提醒、账户恢复、隐私开关、问题反馈 | 直接影响付费信任与日常可用性 |
| 首版补强 | 联系人语言记忆、常用词、单条复制/修正、长文折叠、键盘与可读性 | 减少每天重复操作 |
| 稳定后 | 用户主动选择的图片文字翻译、语音消息转写与翻译 | 有真实需求再做；上传前说明，费用按适当单位或识别后文本明确计算 |
| 验证后 | macOS、选择性的设备同步、月度套餐 | 看流失原因、设备需求和复购，不能只因为竞品有就扩张 |
| 暂缓 | 实时通话翻译、自动替用户聊天、群发、CRM、代理分销、更多平台 | 实现和维护范围大，不能修复当前核心可靠性问题 |

图片、表情、贴纸、音视频文件的原生收发属于聊天基础，需优先验收。图片文字识别、语音转写、通话翻译属于新的 AI 服务，不应混成“已有全功能”。

## 14. 分阶段推进

下列工期只是专注开发与实机测试情况下的排期区间，不是承诺。现有缺陷复杂度、平台审查、支付开户和签名申请均可能影响时长。每阶段以验收结果结束，不以日期到了为准。

| 阶段 | 参考安排 | 主要交付 | 进入下一阶段条件 |
| --- | --- | --- | --- |
| 规则与可行性 | 3–5 个工作日启动，外部审查另计 | 目标市场、计费规则、套餐容量、数据路径、授权问题清单 | 商业方案无已知无法解决的接入障碍，关键规则一致 |
| 核心稳定与隐私 | 1–2 周起，按实测问题调整 | 输入发送、历史、恢复、媒体通话、限时消息清理、性能报告 | 严重缺陷关闭，真实关键路径通过 |
| 商业功能 | 1–2 周起，可与部分测试交错 | 钱包、支付测试环境、退款、订单对账、管理员保护、签名更新 | 支付故障演练和余额核对通过，经营与服务条款确定 |
| 邀请验证 | 10–20 人，持续 2–4 周 | 先免费验证，再在具备条件并获准后少量付费 | 能完成首次使用，有持续聊天和付费意愿，成本可信 |
| 受控扩大 | 首批验证后再安排 | 50–100 人范围、客服和运行观察 | 可靠性、退款、成本和支持能力可以承受 |

现阶段暂不上线。计划讨论和本地开发不等于公开销售授权；达到验收条件后再决定发布。

## 15. 验收标准要能拿出记录

| 类别 | 建议标准与证据 |
| --- | --- |
| 输入与发送 | 真实 Windows 输入法、连续 20 条、联系人切换和附件组合不吞字、不串会话、不重复提交 |
| 恢复 | 翻译前、翻译中、平台提交后和回执未知各阶段断网/重启，原任务与账本可恢复 |
| 字符 | 重试及缓存恢复不重复扣费；可用余额加预留等于已结算余额；各项增加、消费、退回可对账 |
| 支付 | 同一付款重复和乱序通知、补查以及重复退款只产生一次应有的业务效果 |
| 媒体与通话 | 双向图片、视频、文件、语音、表情/贴纸/GIF，15 分钟通话和设备切换逐项记录 |
| 隐私 | 限时和删除消息不在缓存、任务、通知中复现；诊断默认无聊天正文及密钥 |
| 性能 | 健康网络短文本翻译 p95 不高于 3 秒、切换 p95 不高于 500 毫秒作为待测目标；输入保持流畅 |
| 长时间运行 | 一至两个账号先做 8 小时、托盘、锁屏和休眠唤醒测试，记录实际 CPU/内存变化 |
| 升级 | 安装、覆盖更新、中断、保存失败、兼容恢复均有独立数据目录与真实安装记录 |

测试中一旦出现重复扣费、重复发送、发错会话、草稿丢失或付款无法对账，应停止扩大试用并修复。有限样本没有发现问题，不等于可以宣称永不出错或 99.99% 可用。

体验指标记录首次成功翻译率、首次关联耗时、有效使用者次周是否继续使用、试用后购买率、再次购买率、退款原因、每百名用户问题量和实际支持耗时。不要用注册量或安装量代替真实价值。

海外用户试用还要问清三个问题：他们平时在哪种设备聊天；愿意让哪些消息进入云翻译；如果停止使用，原因是价格、翻译质量、平台兼容还是桌面使用频率。它们决定后续投向。

## 16. 第一轮应交付的具体成果

1. 一页消费者计费规则与字符计算示例，确认双向翻译、历史、重试和故障补偿口径。
2. 一个简洁的钱包和三档容量购买原型，英文完整可读，暂不公布未核算售价。
3. 真实文字、媒体、通话、刷新、重启、休眠的缺陷与验收清单，按影响排序关闭。
4. 限时消息清理、用户保留期和云翻译告知方案。
5. 支付与退款测试环境、重复通知测试、字符账本对账报告。
6. 两周实际用量成本报告及价格建议，明确计算值与账单确认值。
7. 管理员保护、签名更新、源码与平台条款审查结果。
8. 10–20 名真实目标用户的邀请测试计划，以及支持、退款和停止扩大试用的处理办法。

这八项组成首轮商业化准备；已存在的模块以补齐和验收为主，不重复推倒重做。
