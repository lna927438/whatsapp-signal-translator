# HelloDog 优化升级建议与验收清单

日期：2026-09-12。当前安排：先本地测试，不发布本轮更新。

建议按“发送可靠 → 翻译与对账 → 完整聊天与媒体 → 性能与发布”的顺序推进。以下指标是建议验收目标，不代表已经达到；已有功能也需要按这些场景验证。

## 本轮已经修复的范围

- Signal 右键“刷新页面”此前只查询 WhatsApp 页面，导致 Signal 刷新不可用。现已接入官方桌面组件；空闲时刷新页面，有草稿、附件、通话或发送任务时保留现场并检查连接。
- 翻译错误此前进入 Signal 的长时间网络重试，消息持续转圈。现在翻译阶段失败会保存该条消息的失败状态，释放队列；45 秒桥接超时不会一直占用发送等待。
- 普通常见英文和能够较明确判断的英文段落，在目标为英语、且未启用语气/术语改写时直接发送，减少反向翻译和不必要的 API 调用。其他语言、混合内容和不确定文本仍需要翻译处理。这不是完整的语言识别系统。
- “拦截中文”遵从目标语言；目标本来就是中文或日语时，不再因汉字而拦截。
- 同一请求的迟到结果不会自动生成另一条发送任务。正常发送不增加审核步骤，异常时使用消息自身的失败和重试入口。

已验证的证据与实际安装包见同目录的本轮修复说明。真实联系人收发、通话以及锁屏后物理键盘操作，需要继续实机验收，不能用模拟测试替代。

## 第一阶段：最优先解决的日常故障

| 优先级 | 方向 | 具体落地内容 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 发送全过程 | 为准备、翻译、上传、交给平台、平台确认分别记录状态与耗时。聊天里只保留简短状态，详细原因放单条消息详情。 | 任一环节失败都有明确结果；永不因一条错误译文永久阻塞后续消息。 |
| P0 | 连续发送 | 翻译可以预处理，发送保持同一对话的顺序；点击/回车共用同一任务；发送后立即腾出输入框。 | 连发 20 条，顺序不乱、不合并不同消息、不重复发送，下一条草稿不被前一条译文覆盖。 |
| P0 | 不确定结果恢复 | 查询原请求和平台原消息编号。区分“明确未发送”和“可能已经发送”。 | 断网、超时、重开后不创建替代发送任务；已确认发送的消息不会再发一次。 |
| P0 | 输入与快捷键 | 真实 Windows 键盘验证 Enter、Shift+Enter、中文候选词、粘贴、多行、emoji、图片附言，以及弹窗后的焦点。 | 中文选词回车不误发；关闭菜单后能立即继续输入；发送键只触发一次。 |
| P0 | 刷新与恢复 | 统一右键刷新、快捷键刷新、重新连接的处理。保留每个联系人的输入、引用、附件及位置。 | 刷新 20 次不掉登录、不丢草稿、不重复扣费；通话和上传中刷新不强行中断任务。 |
| P0 | 真实连接状态 | 分开显示聊天平台、翻译服务、账号登录、代理出口的状态；异常时显示最相关的一项。 | 翻译服务通了不能显示 Signal 已连通；能区别断网、平台离线、登录过期和余额不足。 |

发送链路的“已发送、已送达、已读”必须根据平台证据显示。对方未读不等于发送失败；Signal 官方也区分这些状态，并列出网络、附件和验证等可能原因。[Signal 官方发送故障说明](https://support.signal.org/hc/en-us/articles/360009303072-Troubleshooting-sending-messages)

建议计时目标：输入和按钮反馈 95% 在 100 毫秒以内；健康网络下，200 字以内普通文本翻译的 95% 在 3 秒以内。分别统计排队和服务端耗时，不能通过提前显示“已发送”来让数字变好。超过正常时间先提示等待，达到上限转入可恢复状态。

## 第二阶段：翻译可信、历史不乱、费用可核对

| 优先级 | 方向 | 具体落地内容 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 语言方向 | 增加可靠的语言检测及置信度；低置信度交给翻译服务自动识别。联系人语言记忆与账号默认分开。 | 已是目标语言的普通消息不被翻成反方向；英文、西语、葡语、混合语言、姓名、缩写分别测试。 |
| P0 | 译文质量校验 | 校验目标语言、空结果、数字、URL、邮箱、金额、日期和术语；修正失败与原消息发送解耦。 | 原文中的号码、链接和金额不被改写；译文不正确时不会自动发送错误内容或偷偷发送原文。 |
| P0 | 历史翻译 | 已翻译的同一消息从记录恢复；历史采用可见区域加载；正在编辑/发送的任务优先。 | 重开、切换联系人、向上加载同一条历史均不重复扣费。文字相同但消息编号不同的两条消息保持独立。 |
| P0 | 扣费与费用 | 字符余额、翻译请求、平台消息、API 用量分账关联；保存实际模型、实际 tokens、价格版本和结算结果。 | 一条收费翻译有唯一记录；缓存恢复为零新增收费；未知结果显示待确认；日报汇总能回到每条明细。 |
| P1 | 单条修正 | 允许修改已完成译文、恢复原译文、复制原文/译文；重新翻译与本地修正区分。 | 本地编辑不再调用 API；主动重新翻译清楚标识新操作及可能的费用。 |
| P1 | 语气与术语 | 自然/商务语气，账号默认、联系人覆盖、单条覆盖；专业术语可导入、启用和撤销。 | 只影响指定范围；不会把普通聊天强行扩写，不添加原文没有的信息。 |
| P1 | 显示一致性 | 原文/译文层次、字体、颜色、行距和隐藏开关统一；撤回、编辑、限时消息同步更新。 | 不盖住时间与回执；不会重复插入多份译文；限时内容失效后不能从翻译缓存重新显示。 |

### 美元成本应该怎么算

不要用固定“多少字符等于多少 tokens”计算实际成本。API 返回的 `usage` 才是每次处理的真实 token 依据；离线分词或字符比例只能用于预估。[DeepSeek 官方 Token 用量说明](https://api-docs.deepseek.com/zh-cn/quick_start/token_usage/)

建议保存：请求时间、用户、账号、平台、翻译请求编号、供应商请求编号、实际模型版本、输入 tokens、缓存输入 tokens、输出 tokens、当时价格表及币种、计算费用、账单确认费用、差额和确认时间。

一般计算结构：

`模型计算成本 = 未缓存输入 tokens × 对应单价 + 缓存输入 tokens × 对应单价 + 输出 tokens × 对应单价`

如果单价按百万 tokens 标注，结果再除以 1,000,000。输入总量已包含缓存量时，不能把缓存 tokens 重复计入。推理 tokens 是否已包含在输出中也必须按供应商字段定义处理。遇到分时价格，按供应商规则和请求实际时间记录价格快照。

- 如果供应商以人民币计价，先保存原币种，再用明确日期、来源和汇率折算美元；不要冒充供应商美元账单。
- 将“按官方费率计算”“供应商账单确认”“数据待补齐”分开。优惠、赠送余额、税费或账单调整可能产生差额，不能强行抹平。
- 翻译失败可能已经消耗供应商资源。用户字符退回与供应商成本是两件事，需要分别记录。
- 没有历史 `usage` 的旧记录标为缺失，不补造真实 tokens 或真实费用。
- 面向管理员显示人均/每千字符成本、缓存节省量、失败消耗和每日差异；客户聊天窗口不展示复杂核对表。

## 第三阶段：让完整聊天能力稳定可用

| 优先级 | 方向 | 具体落地内容 | 验收标准 |
| --- | --- | --- | --- |
| P1 | Signal 官方功能 | 建立与固定官方版本对应的功能矩阵，保留账号、联系人、群组、隐私、搜索、归档、屏蔽和安全号码等原生流程。 | 每项标记已接入、模拟通过、实机通过或有问题；不能以编译成功代替“全功能通过”。 |
| P1 | 图片与文件 | 双向图片、视频、音频、语音、文件、贴纸、GIF；粘贴、拖拽、预览、另存为、取消上传。翻译只作用于文字和附言。 | 图片方向正确，中文文件名正常；媒体无需文字也能发送；发送取消和网络失败不会留下永久遮罩或占用输入框。 |
| P1 | 通话 | 单人语音、视频、群组通话、麦克风/摄像头切换、蓝牙耳机、屏幕共享、托盘接听和结束恢复。 | 双向至少 15 分钟通话，窗口切换、缩放、锁屏和设备拔插分别测试；通话结束释放设备。 |
| P1 | WhatsApp 页面适配 | 继续围绕正常网页体验做翻译接入；页面结构变化时检测兼容性，暂停受影响的翻译功能并保留正常聊天。 | 侧栏可拖宽；搜索、归档、右键菜单、媒体、时间和回执不被翻译层遮挡；官方页面更新后有快速回归。 |
| P1 | 多账号隔离 | 登录数据、消息、代理、草稿、联系人语言、缓存和未读都按账号区分。 | 相同联系人名称和相同文本跨账号测试，不能串号；暂停一个账号不会停止其他账号。 |
| P1 | 后台与唤醒 | 分清关闭窗口、托盘运行、暂停账号、退出应用；唤醒后检查连接并恢复原任务。 | 托盘收消息、锁屏、睡眠、网络切换各做 10 轮，不丢草稿、不重复发；关闭并重新打开保持原账号目录。 |
| P1 | 代理 | 分账号检查真实出口；明确哪些平台支持哪种代理，配置失败应明确显示。 | “保存成功”不等于“生效”；连接、媒体下载和通话是否走预期网络逐项验证。 |
| P2 | 聊天效率 | 联系人搜索、未读跳转、可检索的快捷回复、键盘操作说明、复制翻译、对话位置记忆。 | 常用动作尽量一两步完成；快捷回复放入输入框，可编辑后再发送；不会直接误发给当前联系人。 |

Signal 应继续使用官方桌面端作为功能基础，将 HelloDog 的修改集中在窗口管理和翻译接入，减少改动面，并为每次上游升级保留可复现的差异。官方项目包含 Windows 桌面端源码并采用 AGPLv3；发行时保持对应源码、修改说明和许可材料一致。[Signal 官方代码仓库](https://github.com/signalapp/Signal-Desktop)

Windows 的锁屏和睡眠需要分别测试。Electron 提供对应状态事件，但接收到事件不等于业务已经正确恢复。[Electron 电源状态文档](https://www.electronjs.org/docs/latest/api/power-monitor/)

## 管理后台、数据与发布准备

| 优先级 | 方向 | 具体落地内容 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 管理真实用户 | 用户列表、状态、最近活跃、在线版本、最后同步时间、字符余额、用量与请求错误分布。 | 页面能说明数据新鲜度；客户端断线不会一直假在线；管理员操作后客户端正常情况下 5 秒内更新。 |
| P0 | 加减字符 | 指定真实用户、调整数量、原因、幂等操作编号和审计记录；提交后明确成功或待确认。 | 连点、请求超时和刷新只生效一次；余额与账本一致；不能仅依靠前端数值改余额。 |
| P0 | 唯一管理员 | 保持唯一主管理员，最小化后台入口，登录限速、会话到期、密码修改和安全恢复；建议增加二次验证。 | 普通客户端用户无法调用管理员接口；修改密码后可撤销旧会话；恢复方案不会偷偷创建第二个管理员。 |
| P1 | 本地数据保护 | 为含原文/译文、账号令牌和恢复记录的数据设置明确保留期和保护方式；缓存清理与删除账号分开。 | 清缓存不删登录；删除账号入口不隐式清空其他账号；备份恢复在独立目录先验证。 |
| P1 | 隐私与诊断 | 错误记录只保存必要的状态、耗时、版本和脱敏编号；用户发送诊断前可预览；通知可隐藏姓名/内容。 | 默认诊断无密钥、会话令牌、完整聊天内容和附件；管理后台的用量统计不需要展示私人聊天。 |
| P1 | 性能 | 固定测试机，分别测试 1、2、5、10 个账号的启动、切换、收消息、历史滚动、内存和后台 CPU。 | 建议热切换 95% 在 500 毫秒内；8 小时运行后内存能回落，增长超过基线 15% 就调查；指标按账号数量记录。 |
| P1 | 桌面布局 | 独立紧凑账号图标栏、可拖宽聊天列表、合适的最小窗口、多屏位置恢复、100%/125%/150%/200% 缩放。 | 1366×768 下输入框和发送键可见；移除外接屏后窗口不消失；长联系人名不挤掉操作按钮。 |
| P1 | 安装与更新 | 测试版和稳定版分开；安装签名、完整性校验、下载中断续传、安装失败保留旧版。 | 更新中断能继续用原版本；不在通话或发送中强制重启；数据库不兼容时不承诺直接降级。 |
| P2 | 官网与说明 | 截图、版本、支持平台、测试范围、翻译计费和云端处理说明与实际一致。 | 下载页指向已验收版本；不把“已接入”写成“所有功能无差异”。套餐和支付继续暂缓。 |

桌面安全的下一轮检查应覆盖远程页面隔离、权限请求、外部链接与跨进程调用来源校验，不能只检查登录页。[Electron 安全建议](https://www.electronjs.org/docs/latest/tutorial/security) 正式分发前还应完成 Windows 代码签名及实际安装验证。[Electron 代码签名说明](https://www.electronjs.org/docs/latest/tutorial/code-signing)

## 建议安排的五轮验收

1. **文字和键盘**：中英文、混合语言、emoji、空白、长段落、多行、引用、编辑、连发 20 条；同时观察输入响应、顺序和扣费。
2. **断网和故障**：翻译前、翻译中、平台提交中、提交后回执丢失四个时间点断网；重开和切换联系人后核对原任务。模拟 401、余额不足、服务限流、磁盘写入失败和组件退出。
3. **媒体和通话**：图片、GIF、视频、语音、文件双向收发；上传中取消、带附言发送；语音/视频通话和设备切换。仅使用测试账号和同意参与的联系人。
4. **后台和多账号**：5 个账号持续运行 8 小时；托盘、锁屏、休眠、网络切换、多屏、窗口缩放；核对未读、草稿、数据目录和代理隔离。
5. **管理和对账**：管理员加减字符、重复点击、断网后补同步；逐条核对客户端请求、字符账本、供应商 usage 和费用。最后做更新中断与恢复演练。

每次问题记录只需保留：测试版号、平台、发生时间、操作步骤、预期与实际结果、脱敏任务编号。优先提供可复现步骤，不需要把完整聊天内容作为默认附件。

## 何时再考虑正式发布

- P0 项全部通过；发送丢失、重复扣费、串号和不可恢复草稿丢失均为零。
- 两个平台核心文字及媒体场景有实机记录；未验证的通话或高级功能在说明中标明，不能宣称全量通过。
- 至少完成一轮 8 小时多账号稳定性测试与更新恢复测试。
- 管理后台只接真实用户与真实账本；缺失的历史成本数据明确标注。
- 之后先小范围使用、观察失败率和恢复情况，再决定正式发布。更多平台、语音翻译、复杂营销和套餐支付排在这些验收之后。
