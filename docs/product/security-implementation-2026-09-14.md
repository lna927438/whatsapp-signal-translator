## Signal 依赖审计的实际范围

已经应用并测试 uuid 的上游边界修复，保持来源可信度检查，并确认最终 Signal 归档内的四个修复文件与测试文件完全相同。修复来源和锁文件补丁保存在 `security/vendor-patches/`，打包前执行 `scripts/verify-signal-security.mjs`。

**不能报告“Signal 依赖零漏洞”。** 去掉审计忽略项后，整个上游工作区的依赖扫描返回 82 条告警：高危 35、中危 37、低危 10。这个范围包含开发工具、贴纸编辑器及打包组件，不等于客户端存在 82 个可直接利用的入口；也不能仅凭依赖被标记为开发依赖就认定没有运行风险。

例如 Fabric 的告警涉及不可信数据经 SVG 导出进入页面的路径。本轮在 Signal 的应用源码中没有发现 `.toSVG()` 调用，保留这一调用检查结果，但没有将它登记为已经修复。后续需要逐项核对实际打包代码和可达路径，再按兼容性升级，不能靠增加忽略项把报告变绿。[上游安全公告](https://github.com/advisories/GHSA-hfvx-25r5-qc3w)

完整未过滤报告为 `signal-audit-unfiltered.json`；保留原有上游配置的全依赖报告为 `signal-audit-all.json`。本轮没有关闭来源可信度检查，也没有把剩余告警从报告中隐藏。

## 正式启用前仍需完成

1. 购买并完成 Windows 签名身份验证，填入正式发行者和发布公钥；用正式证书重新验收签名与时间戳。目前测试包是 **NotSigned**，生产发布锁仍开启。
2. 由账号持有人绑定真实管理员及 GitHub、Cloudflare、Supabase 的验证器并保管恢复资料。绑定与恢复演练不能用测试验证器代替。
3. 在正式认证服务配置 CAPTCHA、密码策略和平台支持的已泄露密码保护；部署候选数据库迁移、费用保护及保留期任务。这些线上配置本轮均未修改。
4. 确定告警接收渠道，启用正式监控和加密备份计划，并在独立托管环境演练包含 Auth、Storage、角色及配置的完整恢复。本机数据库恢复成功不能替代生产规模演练。
5. 完成 Signal 剩余依赖的兼容性核查及真实 WhatsApp／Signal 双向媒体、通话、系统缩放与重开验证。本轮没有用真实联系人发送消息或拨打电话。
6. 独立渗透测试和正式账号注销留存方案。当前支持停用账号和清理译文；没有增加会级联删除账务的永久注销按钮。相关处置流程已经写入操作说明。
7. 在干净 Windows 构建机验证新手动发布工作流，审阅并提交这次全部源码及锁文件。当前包来自本机未提交工作区，不能仅用基础提交号代表全部打包源码。
