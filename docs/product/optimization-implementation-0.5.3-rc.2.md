## 验证口径

- 必须同时核对一条原生消息的发送和接收翻译请求。只核对发送侧一次扣费并不足以证明没有额外费用。早期 Signal 20 条发送侧检查已被更完整的交叉核对替代。
- 新消息暂时缺少 DOM 方向标记时，已确认的原生消息编号与正文是恢复原文的依据。仅文字相同不是复用其他消息请求的依据。
- WhatsApp 原生虚拟列表不会一次保留所有气泡；连续发送验收上滚收集所有测试消息编号并检查每条注释，不能把 DOM 中暂时缺少的旧气泡误当成发送丢失。
- 4 个 Signal 额外请求本机待确认但云端未找到扣费，继续查询原编号，不主动重新提交。
- 多余扣费补偿合计 705 字符、22 笔。补偿走已有管理接口，原始使用量与扣费保留，未直接改写钱包或删除账本。
- 开发启动器的调试接口、真实资料目录和测试诊断仅用于本机验证，不进入安装包或对应源码压缩包。

## 原生编辑器参考

使用 Lexical 的编辑器状态、范围选择和同步更新能力，并核对底层文本和 DOM 文本一致。编辑器实例或相关能力不可用时沿用已有受保护的编辑路径。参考 [Lexical 官方文档](https://lexical.dev/docs/concepts/editor-state)。HelloDog 对 WhatsApp 的适配仍须跟随网页变更实测。
